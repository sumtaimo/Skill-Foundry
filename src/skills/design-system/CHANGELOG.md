# Changelog

## 1.1.0 - 2026-11-20

- Optional 2026 token group (R-design-system-22), added only when the user asks for glass or frosted panels, a glow, glossy buttons, z-index layers, 2026 or modern effects, or the ui-craft tokens: the engine flag `--modern` writes `--glass-bg` (surface-default at 72% alpha, light and dark), `--glass-blur` 12px, `--r-xs` to `--r-xl` (4, 6, 10, 14, 16 px), `--z-sticky`, `--z-dropdown`, `--z-command`, `--z-modal`, `--z-toast` (20 to 100), `--glow` (brand at 10% light, 16% dark), `--btn-gloss` and `--font-weight-medium: 500`. The names match ui-craft exactly. In design-tokens.json they sit under `modern`; the medium weight under `font.weight.medium`.
- Every 1.0.0 token, the mid-tone rule and the 14 earlier cases are unchanged; without the ask the group is never added (R-design-system-7 now allows the third weight only in this group).
- Path c: the group is a gap family like the others; a user token with the same name (for example `--z-modal`) is never written again.
- A web font is still used only when the user names one: its name goes first in the stack and the user loads the files; no imports or links are added.
- The report of the 2026 group is one short line; layers 07, 08 and 09 and SKILL.md say again that the reply starts with the "## Design system:" heading.
- New live eval cases `modern-glass`, `modern-midtone` and `modern-not-asked` (17 cases).

## 1.0.0 - 2026-11-15

- First version: one design-token set from a hex colour (path a), a style description (path b) or an existing design system (path c, gaps only, never overwriting), with rules R-design-system-1 to R-design-system-18.
- Engine `engine/tokens.mjs` (Node.js, no dependencies) builds the scales, roles and files, and checks every text pair in light and dark mode, so the numbers come from the skill, not from the agent.
- Five style archetypes as numbers (type sizes, radius, control heights, density, shadow, motion, brand share): precise-fintech, calm-workspace, bold-consumer, editorial, dense-data-tool.
- Writes design-tokens.json (W3C design tokens format), tokens.css (light, dark by system setting and by data-theme, density and reduced motion) and a report with every ratio.
- Exact sentences for nothing to build from, a brand colour named only in words, and a request to design a screen.
- Mid-tone brand colours (approved by the owner): when neither white nor the dark ink reaches 4.5:1 on the given hex (for example #0d9488), the filled primary button uses the nearest darker step of the same hue where white text reaches 4.5:1; black text on the given hex is used only when no darker step can carry white. The same applies to a given accent. The given hex stays unchanged at its step and as the new `--color-brand` token (`color.brand`), and the report shows both ratios (white on the given hex and white on the fill). Light colours such as a yellow keep their hex as the fill with dark text.
- Scales no longer turn bright in the middle: saturation eases toward the palest and darkest steps, and steps 400 to 700 are never more colourful (HSL chroma) than the input, so a teal like #0d9488 gives 400 #6bddd3 and 500 #4dc6bb instead of a bright cyan. The hue is kept exactly as before (same drift limits); R-design-system-1 now says this.
- New live eval case `midtone-teal` (11 cases).
- The fixed sentences (nothing to build from, a screen request) are now the whole reply even when the request also asks for a report of files, checks and open items: a fresh agent had added such a list after the decline sentence.
- S1: the skill tells the agent to run the engine as ONE plain command with the path of the script (`node <skill folder>/engine/tokens.mjs ...`), no `cd`, no shell variable, no pipe, no `;` or `&&`, and to say plainly in an open question when it could not run it (R-design-system-19). The engine's own output now says the same: after a run it says the report is its own result, and on an error it says what to do and gives the open-question sentence for a hand build. New live eval case `engine-one-command`.
- S5: on path c the engine detects a family as present only when at least 3 of the user's tokens match it (R-design-system-20). With 1 or 2 matches the family is partly present and its missing tokens are written to the gap files by name, never over a user token, also not in the dark shadows, reduced-motion or density blocks (a single `--gutter` no longer hides the spacing scale, a single `--radius-card` no longer hides the radius scale, a single brand colour no longer hides the primary scale). Colour families also count role tokens whose value is a `var()` or an alias. The report lists each partly present family with the tokens added.
- S5: the neutral scale is built from the project's own greys when it has any (R-design-system-21): they are found by value, kept at their value at the nearest step, the missing steps are interpolated, and the palest and darkest steps take the greys' tint; the result is contrast-checked and the default tinted scale is used, with the reason in the report, only when it cannot pass. New live eval case `existing-partial`; `existing-gaps` re-recorded.
