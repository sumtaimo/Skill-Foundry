# Layer 06: States and edge cases

1. Nothing to build from: reply with the brief of layer 03, step 7. Produce nothing else.
2. A request to design or build a screen, page, mockup, component or flow (for example "design our dashboard screen"): reply exactly "This skill builds design tokens, not screens. For finished screen code, use ui-polish." That one sentence is the whole reply, even when you were asked for a report of files, checks and open items: add no list, summary or note before or after it. Write no files and no markup, and stop.
3. "Like <brand>" or "in the style of <brand>": map the product to the nearest archetype by what it is (a bank or payments product is precise-fintech; a notes or planning product is calm-workspace; a shop, game or social product is bold-consumer; a magazine or news product is editorial; an admin, analytics or developer product is dense-data-tool). Never write the brand name in a file, a flag or the reply; write "the product you named". When you do not know the product and the request has no other cue, use calm-workspace and add an open question asking what kind of product it is.
4. A given hex that fails with white text: a light colour (for example a light yellow) on which the dark ink reaches 4.5:1 stays the primary action fill with dark text. A mid-tone (for example a teal like #0d9488: neither white nor the dark ink reaches 4.5:1) stays unchanged in its scale and as `--color-brand`, and the engine moves the filled button to the nearest darker step of the same hue where white text reaches 4.5:1; black text on the given colour is used only when no darker step can carry white. The report shows both ratios: white on the given hex and white on the fill. Never change the given hex itself.
5. A given hex close to a status hue (for example a red primary): keep it; add the open question "Your primary and danger colours look alike; should errors use a different red?".
6. A grey, black or white given colour: it has no hue to keep; the engine builds a grey scale. Say so in the why line.
7. Three-digit hex (#0f7): expand it to six digits (#00ff77) and use that; write the six-digit form.
8. Path c with every group present: the engine writes only the report and says "No gaps found."; reply with the report.
9. Path c with gap files already in the output folder: the engine stops. Ask the user whether to replace them; never pass `--force` without a yes.
10. A request for one group only (for example "just a spacing scale"): build the whole set anyway, because the groups depend on each other, and say in Open questions that the other groups can be ignored.
10a. `set` prints REFUSED (a contrast pair would fall below its minimum, an alias would break, or the value cannot be built): nothing was written. The reply is the printout, word for word, with the nearest passing value it names. Never write the value another way.
10b. `set` on a value that is derived (a shadow, the glass fill, the font stack): it exits with its message; give that message and, when it names the variable to change instead (`color/brand`, `font/family/sans`), offer that in one sentence.
10c. A request to change a variable when design/variables.json does not exist: say there is no foundation yet and give the brief of layer 03, step 7. A request for a product foundation when design/variables.json exists: do not start again; offer `set`, `check` or `explain` in one sentence.
10d. `check` says DRIFT (a generated file was edited by hand): tell the user plainly and offer `build`, which writes the files again from variables.json and loses the hand edits; run it only after a yes.
10e. One request that needs `init` and then `set` (or `check`): the reply starts with the report of `init` (its first line is the "## Design system:" heading), then one blank line, then the printout of each later command, one paragraph each, and nothing else. A reply that has only the last printout is wrong.
11. Reply in a short, direct tone; do not apologise or explain the fixed sentences further.
