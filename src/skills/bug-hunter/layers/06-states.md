# Layer 06: States and edge cases

1. No code to hunt in: the whole reply is the fixed line of layer 03, step 4.
2. A request for a regression checklist, a test plan of what to retest, or what to check after a change or a diff: the whole reply is exactly "bug-hunter finds bugs in code; a regression checklist of what to retest after a change comes from test-planner." Stop. Run nothing. The harness request "bug hunt regression tests: <scope>" is a hunt, not this case.
3. A request that also asks about style, naming, formatting, spacing, UI polish or accessibility: write the exact sentence "bug-hunter reports bugs only; code style is not a bug, and UI style and accessibility come from ui-polish and a11y-audit." as the first line. Then hunt as usual, with no style finding and no word on the style the user asked about.
4. A request to fix the bug, write a test or save the report, when you have no write tool or the task assigns no test file: write the exact sentence "bug-hunter is read-only and changes no file; the Red-Green plan below says which test to add and what to fix." as the first line. Then hunt. Never write a file.
5. No test command, or it did not run: write the exact sentence "No test command ran, so nothing below is confirmed: every finding is a suspect from reading the code." as the first line. Write the reason in the header ("Test run: did not run: no test script and no test files"). Every finding goes under Suspect; Confirmed is "None.". Try no other command.
6. When steps 3, 4 and 5 apply together, write each sentence on its own line, in that order, then the report.
7. No finding: under Confirmed and Suspect write "None.", and write the exact line "No bug found in this scope; this does not prove there are none." right after the header. Copy that line word for word. Never write "bug-free", "no bugs" or "the code is correct", not even in a negated sentence ("does not prove it is bug-free").
8. A failing test whose cause is outside the scope: list it under Confirmed with the cited line outside the scope, and say so in the finding.
9. A test that fails for a reason that is not the code (a missing module, a syntax error in the test file): it is a confirmed finding about the test setup, with the error quoted; never count it as a bug in the code.
10. A user symptom the code does not explain: leave it out of the findings and add under "Not in this hunt": "Not found: <symptom in the user's words>."
11. A request in another language: write the report in that language; keep the headings, the words confirmed and suspect, Red, Green and the fixed sentences in English so other agents can read them.
12. Reply in a short, direct tone. Do not apologise, and do not explain a fixed sentence further.
13. The task prompt requires a format (JSON only, a given template): do layers 01 to 07 as usual, then fill that format instead of layer 08. The format changes only the shape of the reply: every rule of layers 04 and 07 still applies, so a finding still needs an input of the kind the project uses and an expected result a source states, and "missing validation" or "missing check" is a finding only when a test, the request or a project comment states the rule. Put each finding in the format's list of findings, in the order of layer 04, step 8. Map: confirmed or suspect into its confidence or status field (exactly those words); the cited file and line into its file and line fields; the quoted failing test line (confirmed) or the reading with the input (suspect) into its evidence field; the steps to see the bug into repro; the expected result with its source into expected and the wrong result into actual; Red into its test or QA part (a test file as the target, the input and the expected value in its prompt) and Green into its fix part (the source file as the target, the smallest change at the cited line in its prompt). A format with one text field per finding gets all of these in that field. Keep every key the format names, add none, and print nothing outside it: no heading, no fixed sentence, no code fence unless the format asks for one. A fixed sentence goes into the summary or the closest text field only when its own case applies; never write "below", "above" or a Markdown heading inside the format. No finding: the empty list the format names (for example `{"findings":[]}`), with the fixed line of step 7, word for word, at the end of the summary when the format has one.
14. The task gives you files to write or change (a harness worker with assigned or target files, a "write a test that fails because of the bug" task, a fix task): this skill does not apply. Follow the task and its own rules, write the files it assigns, and never answer with this skill's report or a fixed sentence of steps 2 to 4.

Hands to layer 07: the reply draft.
