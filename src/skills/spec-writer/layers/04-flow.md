# Layer 04: Flow

1. Split the requirement text into statements, in the order the text gives them. One sentence may hold several statements.
2. Mark each statement that the text says is not included ("out of scope", "not part of", "later", "excluded", "not in this release") as an exclusion. It never becomes a clause.
3. Mark each statement whose only content is a vague word (for example "the page must be fast") as vague. It never becomes a clause; clause 10 handles it.
4. Give every other statement exactly one heading:
   - **Main path**: what the user does and gets when everything is valid.
   - **Validation and errors**: what happens with wrong, missing or rejected input, including a rule on what the user types (length, format) and any error message.
   - **Permissions and roles**: who may or may not do or see something.
   - **Empty, loading and disabled states**: what is shown when there is nothing to show, while waiting, or when a control cannot be used.
   - **Persistence after reload**: what is still there after a reload, a new session or a return to the screen.
   - **Limits**: a stated cap on a count, a size, a rate or a time (for example "at most 5 per order", "expires after 30 minutes").
5. When a statement fits two headings, use the more specific one: a statement that names a role goes under "Permissions and roles"; a statement about a reload goes under "Persistence after reload"; a statement with a cap goes under "Limits"; otherwise use the first heading in the list of clause 4 that fits.
6. Write one clause for each statement: "AC-n. Given <precondition>, when <one action>, then <one observable result>." Take the precondition, the action and the result from the statement. When the statement gives no precondition, use the role or the screen the text names; when the text names none, write "Given the feature is available".
7. Write one behaviour and one result per clause. When a statement holds two results, write two clauses, each with its own source phrase. Never join two results with "and".
8. End every clause with its source phrase in italics: the words of the statement, copied without change from the requirement text. Do not shorten the inside of a phrase with "..." and do not correct its spelling. Two clauses never share one source phrase.
9. Decide for every gap whether it blocks. Take the statement the gap belongs to and try to write its clause with only the words of the text. When the clause cannot be written or cannot be tested because a value (a size, a count, a time), a role, a state or a result is missing, the gap is blocking: write a blocking question and no clause for what is missing. When the statement itself gives a testable clause, write that clause, and a missing detail around it is minor. A heading with no statement is never a reason for a blocking question: nothing in the text depends on it.
10. For every vague word, write a blocking question exactly in this shape: `What measurable value defines "<word>" for <thing the text applies it to>?` Quote the word as the text writes it. Add no number, no unit and no example. It is always blocking and it blocks the source phrase that holds the word.
11. When two statements disagree (for example "up to 5" and "at most 3"), write a clause for neither. Write one blocking question that starts with "Conflict:" and quotes both; it blocks both source phrases.
12. Write every blocking question on one line in this form: `- [blocking] <Heading name>: <question>? Blocks: <AC-n or "<source phrase>">`. Start with the tag `[blocking]`, then the heading it belongs to and a colon. After the question mark write `Blocks:` and the exact thing it blocks: the id of the clause that cannot be tested without the answer, or, when no clause could be written, a source phrase copied from the text between quotation marks. A question that cannot name what it blocks is not blocking; treat it as minor (clause 13) or drop it. A question never suggests an answer: no "for example", no "such as", no option list, no value. There is no fixed cap on the number of blocking questions, per heading or in total: write one for every blocking gap, and no more. List them all first, in the order of the headings, then the minor lines.
13. Keep minor questions few. Drop a minor question when it only restates a default: a generic failure or error message, a loading indicator, what a reload keeps, who else may use the feature, or any heading the text says nothing about when no stated clause depends on it; also drop one the clauses already answer. Merge the rest into at most three lines in this form: `- [minor] <Heading name>: <question>? <Heading name>: <question>?`. A line holds at most two questions, related ones together; each question still starts with its heading name and a colon and ends with a question mark. Write no `[minor]` line when no minor question remains. A text with all statements clear has no minor line at all.
14. Write one "Out of scope" line for each exclusion, ending with its source phrase in italics. Write nothing there that the text does not exclude.
15. Number the clauses AC-1 to AC-N in one run, in heading order, with no restart at a heading. Drop every heading that has no clause.
16. Hand the clauses, the open questions and the out-of-scope lines to layer 05.
